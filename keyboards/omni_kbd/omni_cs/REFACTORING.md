# omni_cs リファクタリング調査・計画

## 目的と制約

`omni_kbd/omni_cs` の可読性と保守性を、既存のキーボード動作を維持したまま改善する。
変更は `keyboards/omni_kbd` 内に限定し、挙動変更が必要な事項は実装前に確認する。

LCD仮想キーの表示用レイヤー、matrix座標、実行時のレイヤー解決については、
[`VIRTUAL_KEYS.md`](VIRTUAL_KEYS.md)に現在の仕様と処理経路を記録する。

## 現在の構成

- `omni_cs/omni_cs.c`: QMK のキーボードフックを起点に、起動、LCD、2 個の
  PMW3360、スリープ、独自キーコード、Vial キーマップ更新を統括する。
- `omni_cs/matrix.c`: 物理キーの duplex matrix と LCD 上の仮想キーを一つの
  QMK matrix として走査する。
- `common/touch_lcd_omni.c`: タッチイベントの表示モード別配送と、表示モードに応じた
  再描画の調停を扱う。
- `common/touch_input.c`: RP2040 GPIO のエッジイベントを一定間隔で集計し、タッチの
  接触開始・終了を判定する。ハードウェア依存の接触検出状態はこのモジュールが所有する。
- `common/touch_gesture.c`: 接触開始座標から押下・スワイプを判定し、単発入力、長押し、
  リピート、離脱リセットの状態遷移と、タッチ間隔設定、仮想キー押下状態を所有する。
- `common/touch_key_view.c`: タッチキー画面の画像配置、選択中カテゴリ・レイヤー、
  スワイプによる画面遷移、円形キーのヒットテストを所有する。
- `common/swipe_gesture.c`: スワイプ画面の4プロファイル、選択中プロファイル、描画、
  ジェスチャーに対応するキー送出を所有する。
- `common/status_view.c`, `view_keymap.c`, `sleeping_view.c`: ステータス画面、
  キーマップ画面、スリープ画面を描画する。
- `common/omni_layers.h`: 複数の表示モジュールが参照するキーボードレイヤー定数を定義する。
- `common/omni_virtual_keys.h`: LCDの4ページ×3カテゴリ×6キーと、matrix row 4〜15の
  対応、アイコン表示元の`_FUNC`レイヤーを定義する。
- `common/omni_keycode_encoding.h`: マクロ番号、アイコン番号、dynamic keymap内の保存値が
  `0x7700 + 値`を共有する既存互換表現を、用途別の名前を持つAPIとして定義する。
- `common/trackball_omni.c`: カーソル、スクロール、慣性スクロールの変換を行う。
- `common/trackball_tuning.c`: トラックボール調整画面の描画、タッチ領域判定、設定保存を扱う。
- `common/config_omni.c`: EEPROM 上の設定値を読み書きする。
- `drivers/`: CST816T タッチコントローラと PMW3360 の低レベルドライバ。
- `font/`, `icon/`: Quantum Painter 用の生成済みリソース。
- `icon/omni_image_loader.c`: 生成済み画像を読み込み、画像ハンドルを所有する。
- `omni_cs/rules.mk`: 上記ソースと生成済み画像を列挙するビルド定義。

## 主な処理の流れ

1. `matrix_init_user()` が LCD バックライト、I2C、タッチ割り込み入力、仮想キーを初期化する。
2. `keyboard_post_init_kb()` が EEPROM 設定、LCD、フォント、タッチ IC、画像を初期化する。
3. `matrix_scan_custom()` が物理 matrix とタッチ由来の仮想キーを走査する。
4. `pointing_device_task_kb()` が左右センサーを読み、モードに応じてカーソルまたは
   高解像度スクロールへ変換し、レイヤーに応じて表示を更新する。
5. `matrix_scan_user()` と `housekeeping_task_user()` がタッチ処理、起動画面終了、
   LCD スリープと復帰を進める。
6. `process_record_kb()` が色、トラックボールモード、表示モードの独自キーコードを処理する。
7. Vial がキーマップを書き換えた場合、リンク時の wrapper が仮想キーと設定を再読込する。

## 調査で確認した保守性上の課題

- 機能境界を越えるグローバル変数が多く、所有元と更新箇所を追いにくい。
- `omni_cs.c` が複数の責務を持ち、長い条件分岐と初期化処理が混在している。
- matrix の半分、仮想キー数、LCD 上の円数などが式や数値で繰り返されている。
- `matrix.c` には重複する GPIO 初期化、常に同じ値を返すための冗長な条件、
  未使用引数がある。
- 命名、括弧、空白、コメントの粒度がファイル内でも統一されていない。
- 生成済み画像 100 個前後が `rules.mk` に個別列挙され、変更時の確認が難しい。
- 一部の公開ヘッダーが実装詳細の状態を多数 `extern` で公開している。
- LCDアイコンは`_FUNC`レイヤーの仮想キーを参照する一方、タップはアクティブレイヤーの
  同じmatrix座標として処理される。表示用と実行用のレイヤーを別々に変更すると不一致になる。
- 仮想キーは既存の押下パルスタイミングを維持するため、QMKの確定済み`matrix`を直接更新する。
  配列外アクセスと配列配置依存は解消したが、QMKが公開setterを持たないため内部シンボルへの
  依存は残る。QMK更新時には`matrix_common.c`の定義を確認する必要がある。
- dynamic keymapの`_NUM`、`_MOUSE`レイヤー内を本体設定の保存領域にも流用している。
  EEPROM互換性のため当面は座標と符号化をAPIで隠蔽し、将来は専用保存領域への移行を検討する。

## 命名方針

- 変数名と構造体メンバー名には役割が分かる名前を使い、一部例外を除き、基本的に1 文字の識別子は使用しない。
- ループ変数も `image_index`、`row_index` のように対象を名前で示す。（短縮形としてidx程度は認める）
- 純粋に座標を指すなら `x`、`y`という命名を認めるが、移動量であれば `delta_x`、`delta_y` のように明示する。
- その他例外として、明確に幅、高さを示したい場合のw,hなどや、完全に意味を持たないループカウンタとしてのi（単に10回繰り返したいだけの場合にi<10とするようなもの）などは1文字でもよいものとする。
- 外部ライブラリが定義する型やメンバー名は変更対象外とする。

## 実施計画

### フェーズ 1: 動作を変えない局所整理

- 用途が明確な定数を名前付きにし、ループと境界計算を読みやすくする。
- `omni_cs.c` の長い処理を責務別の `static` helper に分割する。
- `matrix.c` の重複初期化、未使用引数、冗長な条件を整理する。
- 各段階で `make omni_kbd/omni_cs:vial` が成功することを確認する。

### フェーズ 2: モジュール境界の整理

- 共有状態の所有元を決め、直接参照を getter/setter または状態構造体へ寄せる。
- LCD、タッチ、設定、トラックボール間の公開 API を必要最小限にする。
- `omni_cs.c` から独立可能な制御処理を `common/` の適切なモジュールへ移す。

### フェーズ 3: ビルド定義と未使用コードの整理

- 生成リソースの列挙方法を整理し、追加・削除時の手順を文書化する。
- 参照関係を確認して未使用コードを候補化する。
- 削除やタイミング変更など挙動に影響し得る変更は、候補と影響を提示して確認後に行う。

## 今後の推奨対象

1. `status_view.c` の内部整理。現時点で手書きソース中最大の473行であり、短縮名、数値定数、
   描画と入力処理の重複が残る。設定保存との結合が強いため、小さな単位で進める。
2. `config_omni.c/.h` の公開状態整理。色、トラックボール曲線、OS別バッファが直接公開
   されている。EEPROMとVialの互換性を維持する必要があるため、API化は項目群ごとに行う。
3. `rules.mk` の生成画像列挙整理。実行時挙動へのリスクは低いが、QMKのmake変数展開と
   生成物の追加・欠落検出を確認してから変更する。
4. 未使用候補の確認と削除。現在は `process_tap_report()` と
   `OMNI_SCROLL_INERTIA_AXIS_SWITCH_RATIO` が参照されていない。

## 検証方針

- 基準ビルド: `make omni_kbd/omni_cs:vial`（調査開始時点で成功）。
- 各フェーズで同じコマンドによるコンパイル・リンク・UF2 生成を確認する。
- 実機確認では物理キー、LCD 仮想キー、左右トラックボール各モード、慣性スクロール、
  全表示モード、Vial 更新、スリープ・復帰、サスペンドを確認する。
